# MergeFlow – Project Memory

## Architecture Decisions

- **Routing**: `/projects` → Migration Hub, `/projects/[id]` → dashboard (redirects to setup if not complete), `/projects/[id]/setup` → guided 6-step setup flow, `/projects/[id]/requirements` → destination requirements, `/projects/[id]/review` → review workspace, `/projects/[id]/schema` → schema & rules, `/projects/[id]/audit` → audit log
- **CSV import**: Parsed entirely client-side in the browser (no streaming), then rows are POSTed to `importSourceFile` in batches of 100. Max practical import is ~1000 rows per file due to request size.
- **AI analysis**: Uses `ai.singleResponse` with a JSON-format prompt. `analyzeRecords` runs deterministic validation + duplicate detection ONLY (no AI) — each AI call takes 10-20s and `setTimeout` is unavailable in the server runtime, making it impossible to safely bound AI time in a bulk function. AI analysis runs on-demand per record via `analyzeRecordAI(recordId, projectId)` which is called from the "Analyze with AI" button in the review panel. This is the only architecture that avoids the 40s server function timeout.
- **Evidence-based AI rule**: AI must ONLY flag concrete source-data evidence (specific field values, undocumented codes, explicit notes, test data signals, direct conflicts). Generic uncertainty — unverifiable uniqueness, theoretical staleness, normal business fields — is strictly prohibited. Source-only `review` policy fields are the primary AI target, but ALL unmapped populated fields plus notes/text fields are now included in AI context. Notes fields (detected by name pattern) are always sent to AI regardless of policy. If AI finds nothing, disposition stays `ready_for_approval` and UI shows "No additional contextual issues found." `AIFinding` now has optional `evidence`, `whyItMatters`, `recommendedAction`, `suggestedQuestion`, `confidence` (per-finding) fields. UI shows human-readable issueType labels ("Needs Clarification", "Test / Non-Production", "Recommended Exclusion") and per-finding confidence. Extended reasoning is hidden behind "View analysis details".
- **Export**: `exportApprovedRecords` returns CSV (destination-mapped fields only, no source-only fields). `getApprovedRecordsData` returns structured rows for client-side xlsx. `getAuditWorkbookData` returns 3-sheet data (Record Summary, Decision Audit Trail, Discussions & Resolutions) for client-side xlsx. The client uses `xlsx` (already installed) to build and download `.xlsx` workbooks with column widths, frozen header rows, and auto-filters. ISO 8601 timestamps are stored and exported consistently; UI displays in locale. Audit workbook and approved export buttons appear on the dashboard header, finalized banner, and audit log page.
- **Auth**: `<Authenticate>` wrapper in root layout. All server functions default to `role: ['user']` (framework default).
- **Analysis findings**: Structured findings split into `destinationRuleFindings` (jsonb, `RuleFinding[]`) and `aiAnalysisFindings` (jsonb, `AIFinding[]`) on `migrationRecordsTable`. Legacy `validationErrors` kept for backward-compat reads. AI prompt explicitly told not to duplicate or contradict deterministic findings. analyzeRecords processes ALL records (no limit) when no `recordIds` passed.
- **Enhanced audit trail**: `auditLogTable` now has `previousState`, `newState`, `reason`, `linkedRecordIds`, `actionContext` columns. Append-only enforced in UI. No-op guard in `updateRecordStatus` and `bulkUpdateRecordStatus` prevents duplicate audit entries when status is unchanged.
- **Consolidation workflow**: `consolidationsTable` stores surviving record, merged record IDs, field selections, and reason. `data/consolidations.server.ts` handles `getConsolidationCandidates` and `finalizeConsolidation`. Merged records are marked `consolidated` (never deleted). Surviving record gets merged field data and returns to `pending` for final human review.
- **Discussion workflow (v2)**: `recordDiscussionsTable` now has `linkedRecordIds` (multi-record bulk discussions), `participants` (app user IDs for in-app notifications), `notifyByEmail` (opt-in email for app users; always email for external stakeholders). `addDiscussion` creates in-app notifications for selected participants, marks all linked records as `discussing`. `bulkExcludeRecords` server function for bulk exclusion with shared reason. `notificationsTable` tracks per-user in-app notifications; `data/notifications.server.ts` exposes `getNotifications`, `markNotificationRead`, `markAllNotificationsRead`, `getAppUsers`. AppHeader shows notification bell with unread badge and dropdown list.
- **Migration Values (Override Layer)**: `migrationValuesTable` (migration 013) stores field-level overrides on top of immutable source data. One row per (record_id, field_name), upserted on each save. Fields: `originalSourceValue` (captured at first save), `migrationValue`, `previousMigrationValue`, `changedById`, `reason`, `discussionId`. `setMigrationValue` in `data/migration-values.server.ts` saves the override, then immediately re-runs deterministic rule validation using effective data (source + overrides) via `validateRecordLocal` (inlined copy of analysis.server.ts `validateRecord`). If all violations clear, `destinationRuleFindings` is set to null and `recommendedDisposition` recalculated. Export (`exportApprovedRecords` and `getApprovedRecordsData`) checks migration value overrides for each record+field before falling back to source data. The UI shows a `RemediationPanel` (expandable) inside each rule violation row, and an "Apply to migration value" section inside `DiscussionThread` and `ResolveDiscussionDialog`. `ResolveDiscussionDialog` now accepts `ruleFindings` and `onMigrationValueSaved` props and calls `setMigrationValue` + `resolveDiscussion` sequentially using plain async functions (not mutation hooks) since `mutateAsync` is not supported by `useServerMutation`. `RecordDetail` calls `useGetRecord` and `useGetMigrationValues` to load discussions with authors/timestamps and current migration value overrides.
- **validateRecord NOT exported**: `validateRecord` in `analysis.server.ts` is a local function. Cross-server imports are not supported (esbuild CDN routing issue). `migration-values.server.ts` inlines its own copy as `validateRecordLocal`.

- **jsonb $type<> not supported**: Use plain `jsonb()` without `.$type<>()` — the framework does not support typed jsonb generics. (ready_for_approval | consolidate | discuss | exclude | needs_manual_review) and `recommendedDispositionReason` (text). Duplicate detection runs as a post-pass across all project records, comparing normalized email/phone/name fields; results stored in `duplicateEvidence` (jsonb, `DuplicateMatch[]`), `duplicateConfidence`, `duplicateRecordIds`. Discuss items get a `suggestedQuestion` from AI.
- **Dashboard clarity**: Dashboard separates Analysis Summary (AI-classified findings: ready_for_approval, rule_violations, duplicates, needs_discussion, recommended_exclusions, ai_findings — from `getQueueCounts`) from Disposition Progress (human decisions: approved, consolidated, excluded, discussing, pending). `getProjectStats` now returns `analyzed` and `withFinalDisposition` counts. Accounted-for metric shows "X of Y records have a final disposition". All dashboard metrics are clickable to filtered Review queue. Completion banner shown when all records have a final disposition.
- **Source-only column policies**: `migrationProjectsTable.sourceColumnPolicies` (jsonb, migration 011) stores per-column policies (`keep` | `ignore` | `review`) for source-only columns. Managed in setup Step 5 via `updateProjectSetup`. Default is `keep`. Policies are informational only — export still excludes all source-only columns regardless of policy.
- **Destination Requirements inline editing**: Requirements table (Step 2) has clickable Required checkbox, clickable Unique checkbox, inline type Select, and `AllowedValuesEditor` (tag UI) for `enum_type` fields — all inline, no modal needed for simple changes.
- **Bulk selection**: Enabled in 5 analysis queues (ready_for_approval, rule_violations, needs_discussion, recommended_exclusions, pending). Bulk actions: Approve (only ready_for_approval, blocked if any selected record has rule violations), Discuss (opens DiscussDialog with linkedRecordIds for all other selected records), Exclude (requires shared reason). No bulk Consolidate. Each action creates individual audit log entries.
- **Duplicate requirement prevention**: `createDestinationField` normalizes field names via `normalizeFieldName` (lowercase, strip spaces/hyphens/underscores) and blocks duplicates with an error. `getDuplicateRequirements` surfaces existing duplicates. Requirements page shows orange banner + highlighted rows for duplicates.
- **Canonical disposition model**: `lib/disposition.ts` defines `FINAL_STATUSES` (approved/consolidated/excluded) and `UNRESOLVED_STATUSES` (pending/discussing). `getFinalizationChecklist` is the single source of truth for all disposition counts (tracked, finalized, unresolved, pending, discussing, approved). All UI surfaces — Review sidebar, FinalizationDialog, Dashboard, Audit — use this. Do NOT recalculate these counts independently.
- **Export vs Complete Migration**: Two distinct concepts. "Export Approved Data" is always available regardless of unresolved records. "Complete Migration" requires all checklist items passing (all records finalized, no open discussions, no blocking violations, mappings/requirements verified). The FinalizationDialog title and sidebar button label switch based on `canFinalize`.
- **Blocking violations**: Rule violations block migration for all statuses EXCEPT `excluded` and `consolidated`. Excluded records won't be migrated so violations are irrelevant; consolidated records are already resolved. This is enforced in `getFinalizationChecklist`.
- **Reference Data**: `referenceFilesTable` stores destination system existing records for cross-system duplicate detection. Uploaded in setup step 3, skippable. Rows stored in `data` jsonb column (added migration 011). Analysis cross-system detection loads these rows and compares using `buildRefRecordIndex`. `importReferenceFile` now requires `rows: Record<string, unknown>[]` param (not just `rowCount`). "Cross-system detection enabled" only shown when `totalRefRecords > 0` (not merely when file metadata exists).
- **Auto-map**: `autoMapFields` server function maps source columns to destination fields by exact and normalized name match. Called automatically on step 5 entry.
- **Requirement labels**: "Human Confirmed" renamed to "Team Verified" throughout. "Confirm" actions renamed to "Verify". "AI Suggested" label kept as-is. Inline Required/Optional toggle and type selector added to requirements table rows (no modal required for simple changes).
- **Analysis outdated warning**: Only shown when `analysisOutdated === true` AND `analyzed > 0`. Never shown when no analysis has run yet. Each `analyzeRecords` run writes a JSON audit log entry including requirement field names, count, and timestamp so previous analysis snapshots are traceable.
- **Destination Requirements**: `requirementSource` distinguishes `'manual'` (auto-confirmed) from `'ai_suggested'` (must be human-confirmed before use). Only `isConfirmed=true` fields are used for rule-based validation in `analyzeRecords`. When confirmed requirements change, `analysisOutdated=true` is set on the project. `getRequirementsStatus` drives dashboard warnings. Template upload uses client-side `xlsx` for CSV+Excel parsing, then calls `suggestRequirementsFromTemplate` (AI call). Rule-based validation errors include `issueSource: 'rule'`; AI issues use separate `aiIssueType`/`aiIssueSummary` fields.

## Theme

ASU-inspired: maroon primary (`oklch(0.38 0.15 20)`), gold secondary (`oklch(0.85 0.18 85)`). Applied via `update_theme`.

- **Duplicate Detection (Evidence-Based Identity Matching)**: Matching requires meaningful identity evidence: exact email, exact phone, high name bigram similarity (>=0.80), or business domain match. `isIdField()` guards `isNameField()` so fields like `customer_id`, `account_id`, `record_id`, etc. are never treated as name signals and never cause conflicts. Categorical fields (account_tier, status, country, industry, etc.) are explicitly excluded via `isCategoricalField()`. Different customer IDs never disqualify a match. Two thresholds: `DUP_SHOW_THRESHOLD=0.65` and `DUP_CONSOLIDATE_THRESHOLD=0.85`. Both source-to-source and source-to-destination matches can recommend `consolidate` disposition when confidence >= 0.85. For s2d, each `DuplicateMatch` carries `referenceData` (the raw reference file row) so `getConsolidationCandidates` can build synthetic `MigrationRecord` objects for reference records (negative IDs). `finalizeConsolidation` handles negative `survivingRecordId` (destination wins): only source records in `mergedRecordIds` get marked `consolidated`; audit trail records `matchCategory: source_to_destination`.

## ConsolidationDialog Loading Pattern

Uses `useEffect` watching `open` prop to trigger `getConsolidationCandidates`. NOT relying on Dialog's `onOpenChange` for data loading (Radix controlled Dialog does not fire `onOpenChange` when `open` is set programmatically from outside).

## Key Constraints

- `sql` template literal does not support type arguments in this framework version — use `sql\`count(*)::int\`` without `<number>`.
- `useServerMutation` returns `.isPending` not `.pending`.
- `redirectToLogout()` takes no arguments.
- `ai.singleResponse()` not `ai.complete()` — returns `unknown`, must cast to string before string operations.
